## 挑战 1：实现方式对性能与精度的影响

工具：`scripts/bench_attention.py`（骨架已给，标了 `NotImplementedError`）

### 要回答的问题

同样的数学、不同的实现，在昇腾 910B 上差多少？

1. **全长注意力**：SDPA vs 昇腾融合算子
2. **滑窗注意力**：同上
3. **RMSNorm**：原生 PyTorch vs `npu_rms_norm` 融合算子
4. 每一项都要给出**数值一致性证据**（不能只看快慢）

### 必须分开测全长层与滑窗层

这是本挑战最值得写进报告的一点：

| | SDPA | 融合算子 | 加速比 |
|---|---|---|---|
| 滑窗层 | 13.42 ms | 6.70 ms | **2.00×** |
| 全长层 | 9.18 ms | 12.42 ms | **0.74×** ← 反而更慢 |

原因：SDPA 在 `Tq == Tk 且全长` 时走 PyTorch 自己的融合内核（很快）；
而**滑窗时必须物化一张 (T,T) 布尔 mask** 再交给 SDPA，于是用不上任何融合。

所以融合算子的收益**只出现在滑窗层**，而 `window_pattern="SSSL"`
意味着 3/4 的层都是滑窗 —— 这才是它值得做的原因。

> **如果你的结论是"融合算子全面更快"，那是没分开测。**

### 必须给出数值一致性证据

只报"更快"是不够的 —— 快而算错没有意义。至少要：

* 与**参考实现**（SDPA）逐元素比对，报告 `max|Δ|`
* 说明这个差值是否只是 **bf16 累加顺序**造成的
* 对 RMSNorm 要额外做一件事：**把 float64 真值也算出来**，
  比较各自相对真值的偏差。否则很容易得出
  "融合算子比原生精度差"这个**错误**结论 —— 实测两者相对真值的偏差
  量级相同，差异只是 bf16 的固有舍入。

## 挑战 2：模型规模对比与 scaling law

工具：`scripts/bench_scaling.py`

```bash
python scripts/bench_scaling.py plan --depths 2 4 6 8   # 先算账，不训练
python scripts/bench_scaling.py sweep --depths 2 4 6 --epochs 2
python scripts/bench_scaling.py fit                      # 拟合
```

### 三件事

1. **小模型先跑通**：用 d2/d4 做代码调试，确认整条链路正确。
   这部分是工程实践，报告里说明你验证了什么。
2. **拟合幂律**：`L = a · N^(-α)`
   * 用**真实参数量**做横轴（`src/budget.py` 有参数量的解析模型，可复用）
   * 报告 α 与 R²
   * **至少 3 个规模**，否则拟合没有意义
3. **最优化**：在固定算力约束 `C = 6ND` 下求最优的 `N_opt` 与 `D_opt`。
   回答："固定算力该投给更大的模型，还是更多的数据？"


### 提示：为什么要把 batch 调小

默认 `--total-batch 32768`（不是大模型常用的 524288）。
因为语料小，batch 太大就没几步了 —— 步数太少看不出趋势。
这也是一个可以写进报告的权衡。
